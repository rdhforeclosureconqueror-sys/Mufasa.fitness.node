# Independent Review Handoff — Private Client Getting Started Checklist v1

## Role
Independently verify this branch. Do not assume the implementation is correct. Do not merge on behalf of the owner.

## Branch
`private-client-getting-started-checklist`

## Goal
Give Private Sessions clients a dependency-aware onboarding checklist from account access through first completed workout, while giving the assigned trainer an immediate view of where each client stopped.

## Required behavior
- Dashboard shows a Getting Started checklist for Private Sessions clients.
- Checklist is derived from canonical user data rather than client-side completion flags.
- Retention Journey and Return Agreement remain client-required.
- Baseline photos and measurements may be completed by the client OR marked to be done in person with trainer.
- `with trainer` means scheduled/pending evidence, not falsely completed evidence.
- Trainer program assignment remains trainer-owned and is not auto-generated by this checklist.
- First workout uses the existing authoritative workout completion / gamification path; do not create a parallel badge ledger.
- Dashboard welcome-back copy always identifies the next actionable step.
- Trainer workspace list/detail surfaces Getting Started progress and `readyForTrainerProgramming`.
- Admin First-Failure checks `/api/me/getting-started`.

## Specific security / data checks
1. GET/PUT Getting Started endpoints require canonical authentication.
2. A member can only update their own photo/measurement handling preferences.
3. Trainer visibility remains constrained by existing assigned-client authorization.
4. No health details, progress photos, or measurements are added to trainer list summaries; detailed data remains inside assigned-client detail.
5. Photo/measurement `trainer` preference does not mark actual evidence complete.

## Acceptance path
1. New Private Sessions client with trial/access accepted and quote submitted.
2. Dashboard shows checklist and Welcome back / next step message.
3. Complete Retention Journey; refresh and confirm checkbox/state advances.
4. Complete Return Agreement; refresh and confirm advance.
5. For photos choose `Take with trainer`; for measurements choose `Do with trainer`.
6. Confirm both say `With trainer`, not `Complete`.
7. Confirm program step becomes Trainer step only after all required client preparation is satisfied.
8. Open Trainer Workspace and verify that client list shows X/Y progress, next step, and READY FOR TRAINER PROGRAMMING when applicable.
9. Assign a program; verify first-workout step becomes Ready.
10. Complete first authoritative workout; verify checklist completes and existing `badge.workout.1_completed` path remains authoritative.
11. Run Admin First-Failure and verify Getting Started API passes.

## Questions for reviewer
- Does the Journey data shape used here match the canonical Journey service in production for all Private Sessions clients?
- Should any assessment requirement remain a hard blocker if more than one assessment is pending? Current v1 treats any completed assessment as satisfying a non-empty pending list and should be tightened if requirements are individually identifiable.
- Should the client be allowed to change `trainer` back to `self` after an appointment is scheduled? V1 permits changing the preference.
